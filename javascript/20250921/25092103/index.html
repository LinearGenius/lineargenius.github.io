[支付接入] 前端对接支付宝与微信支付的完整流程

发表于 2025-09-21 分类于 JavaScript Disqus：

把支付接入拆成创建订单、服务端下单、前端唤起、异步通知、主动查询与退款，建立可信且可恢复的支付状态机。

先确定支付场景

支付宝电脑网站、手机网站和 App 支付，以及微信 JSAPI、小程序、Native、H5 支付的唤起方式不同。前端先根据运行环境选择产品，服务端再调用对应下单接口。商户号、应用私钥、APIv3 密钥和平台证书只能保存在服务端。

订单状态由服务端掌握

创建业务订单时由服务端根据商品快照计算金额，前端只提交商品与优惠选择。订单至少包含商户订单号、金额、币种、用户、渠道、状态和过期时间。商户订单号作为幂等键，重复点击不得创建多笔待支付订单。

服务端下单，前端只负责唤起

服务端向支付宝或微信支付发送签名请求，拿到表单、跳转地址、二维码或 prepay_id，再把有限的唤起参数返回前端。微信 JSAPI 参数需要服务端二次签名；支付宝返回的 form 应从可信接口获得，前端不得拼接私钥签名。

前端回调不能判定支付成功

用户可能关闭页面、网络可能中断，回调参数也可能被伪造。前端唤起结束后显示“正在确认支付”，轮询自己的订单查询接口。最终状态以支付平台异步通知验签后的服务端记录为准；通知可能重复，处理必须幂等。

异步通知必须验签

服务端保留原始请求体，按渠道规范验证签名、证书序列号、时间戳和随机串，并校验商户号、应用 ID、订单号、金额与币种。先完成幂等状态转换和账务记录，再按规范返回成功响应。验签失败绝不能更新订单。

状态机与补偿任务

订单可以从 CREATED 进入 PAYING、PAID、CLOSED，退款再进入 REFUNDING、REFUNDED。禁止从 CLOSED 直接变成 PAID 等非法跳转。定时任务主动查询长时间未确认的订单，处理通知丢失；每日对账发现本地与渠道状态不一致。

退款与异常体验

退款仍由服务端发起并记录唯一退款单号。前端展示“已提交、处理中、已退款、退款失败”，不要在请求超时时直接告诉用户失败。支付按钮提交后立即禁用，但要提供恢复入口；用户返回页面时根据订单号继续查询。

上线前清单

先在沙箱或测试商户验证成功、取消、超时、重复通知、金额不一致和退款。生产环境限制通知来源并依赖签名验证，监控下单成功率、通知延迟和未知状态。任何密钥都不能进入前端包、仓库或埋点。
