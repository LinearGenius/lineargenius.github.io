[登录鉴权] 前端如何安全地使用 JWT

发表于 2025-05-18 分类于 JavaScript Disqus：

围绕登录、续期、退出和权限校验，设计一套前端可落地的 JWT 会话方案，并避开 localStorage 与无限刷新等常见陷阱。

JWT 解决什么问题

JWT 是一种紧凑的声明载体，由 Header、Payload 和 Signature 三部分组成。签名用于发现篡改，不会自动加密 Payload，因此令牌中不能放密码、身份证号等敏感数据。JWT 只是令牌格式，完整登录系统还需要签发、存储、续期、撤销和风控策略。

访问令牌与刷新令牌分工

访问令牌生命周期短，用于调用 API；刷新令牌生命周期更长，只用于换取新访问令牌。前端可以把访问令牌保存在内存，把刷新令牌放入 HttpOnly、Secure、SameSite Cookie，使普通 JavaScript 无法直接读取长期凭据。服务端对刷新令牌做轮换并记录令牌族，发现旧令牌被再次使用时撤销整个会话。

登录与续期流程

登录响应通过 Set-Cookie 写入刷新令牌，并在响应体返回短期访问令牌。页面刷新后内存令牌消失，应用启动时调用一次 /auth/refresh 恢复会话。

并发 401 只刷新一次

多个请求同时过期时，如果每个请求都刷新，会产生竞态和令牌轮换失败。用共享 Promise 把并发刷新合并，成功后仅重放一次原请求；刷新仍失败则清空状态并回到登录页。

前端路由守卫不是权限边界

前端根据用户声明隐藏按钮、阻止进入页面，只能改善体验。攻击者可以直接调用 API，因此服务端必须在每个受保护资源上验证签名、iss、aud、exp 和权限，并避免接受算法降级。角色权限变化后，短期令牌能缩短旧权限继续生效的时间。

退出与多设备会话

退出时调用服务端接口撤销当前刷新令牌并清除 Cookie，再清空内存状态。账户安全页应展示设备、最近活动时间和撤销入口。修改密码、检测到令牌重放或管理员禁用账户时，服务端应能撤销相关会话。

前端安全检查

全站使用 HTTPS；刷新接口检查 Origin 并配置 CSRF 防护；不要把令牌写入 URL、日志和错误监控；不要仅解析 Payload 就当作已验证身份；不要让刷新请求无限循环；敏感操作要求近期重新认证。
