[前端安全] 从 XSS、CSRF 到 CSP 的防护清单

发表于 2026-01-18 分类于 JavaScript Disqus：

用数据流和浏览器安全边界理解 XSS、CSRF、点击劫持与供应链风险，并把编码、净化、CSP 和 Cookie 策略落到工程中。

威胁从不可信数据开始

URL 参数、富文本、接口字段、localStorage、postMessage 和第三方脚本都可能成为不可信输入。安全评审要沿着“来源—转换—危险落点”追踪数据，而不是只搜索 script 标签。innerHTML、insertAdjacentHTML、document.write、eval 和字符串形式的定时器都是高风险落点。

XSS 要按输出上下文处理

React 默认会转义文本插值，但 dangerouslySetInnerHTML 会绕过保护。普通文本使用 textContent；HTML 富文本使用经过配置的净化器；URL 只允许明确协议；不要把用户输入拼进 JavaScript、CSS 或事件属性。不同上下文需要不同编码，统一“替换尖括号”并不可靠。

CSP 提供第二道防线

通过响应头部署 CSP，先使用 Report-Only 收集违规，再逐步移除内联脚本和 unsafe-eval。基于 nonce 或 hash 的 strict CSP 能限制脚本执行来源；object-src none 和 base-uri none 可减少绕过面。CSP 不能替代正确编码与净化。

CSRF 与 Cookie 会话

浏览器会自动携带 Cookie，因此攻击页面可能诱导用户发起带身份的请求。使用 SameSite=Lax 或 Strict、CSRF Token 与 Origin/Referer 校验；修改状态的接口不得使用 GET。XSS 能绕过许多 CSRF 防护，所以两者必须同时治理。

登录凭据与敏感信息

会话 Cookie 使用 HttpOnly、Secure 和最小 Path/Domain。敏感令牌不写 URL，不进入日志和前端错误上报。退出、改密和风险事件要撤销会话。前端环境变量会被打包进静态文件，不能存放真正的秘密。

第三方依赖与供应链

锁定依赖版本，在 CI 中审计高风险更新，减少不必要的第三方脚本。外链静态资源可使用 Subresource Integrity；第三方脚本拥有页面同等权限，应通过 CSP、沙箱 iframe 或服务端代理缩小能力。

文件上传与下载

仅凭扩展名不能判断文件类型。服务端限制大小、解析真实格式、重新编码图片，并把用户文件放在独立域名或强制下载。生成 CSV 时防止公式注入；下载文件设置正确 Content-Type 和 Content-Disposition。

安全回归清单

为富文本、搜索参数、错误消息和跳转 URL 建立攻击样例；检查响应安全头；测试跨站请求、iframe 嵌入和权限越界；把 CSP 报告、登录异常和依赖告警接入监控。修复必须落在共同组件或安全边界上，避免每个页面重复补丁。
